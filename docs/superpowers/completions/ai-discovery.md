# Discovery lane completion

Branch: `ai/discovery`. Baseline: `3da8229`. Scope: parallel-plan Task 3, original Task 4, and the listing/discovery specification. Production changes are confined to `backend/app/github.py` and `backend/app/discovery.py`.

## Concrete gaps fixed

- GitHub JSON and nested repository/release/README payloads now fail with bounded, credential-safe `GithubError` messages. Repository IDs must be positive integers, and public visibility must be explicit. Search URLs and canonical repository/owner URLs are validated before use.
- Every request, including relative or absolute rename redirects, is checked against the fixed HTTPS API host before forwarding authorization. Redirect count, per-request timeout, and the two-megabyte response ceiling remain bounded. HTTP errors include bounded remaining/reset/retry-after headers; no automatic rate-limit retry loop was added.
- `search_repositories(search, limit=20)` retains its `urls`/`incomplete` result shape. It now supports at most four pages and 100 results, handles zero/negative limits without an external request, and flags result truncation as incomplete even when GitHub itself reports a complete search.
- Ancillary metadata comes from the validated canonical repository after a rename. Only a validated stable, non-draft latest release contributes version/activity; a prerelease/draft date cannot make a repository appear active. Release provenance links identify the returned tag. README provenance is recorded only when content was actually decoded. Invalid base64/timestamps are rejected, and requirements remain verbatim bounded excerpts (15,000 README characters, 3,000 requirement characters).
- GitHub topics remain tags and no longer infer platform compatibility. Architectures, attributes, and free-use status remain unknown unless supplied through the existing owner workflow. Descriptions remain upstream text; Jev cannot generate descriptions or fill factual fields.
- Discovery now searches active older repositories as well as seeds, recent repositories, a small-star recent bucket including zero-star projects, and rotating root-category topics. It allocates remaining queue slots across searches to avoid filling the entire default queue with recent results before reaching topics.
- Source collection checkpoints incrementally record planned searches, progress, source limits/results, omitted searches, and incomplete coverage. Original `urls`, `index`, and `incomplete` keys are preserved, as are any unrelated saved keys. Legacy completed-collection checkpoints remain readable.
- A persisted `evaluated` counter advances **before** each repository fetch. Failed/interrupted attempts consume the run allowance, preventing restarts from repeatedly exceeding the configured maximum (hard ceiling 100). Persisted repository IDs prevent rename aliases from producing duplicate decisions, candidate revisions, or star observations within a run.
- Missing repositories are recorded and skipped; other GitHub errors retain the existing owner-response failure boundary. Lease and pause checks surround GitHub/Jev work. Every checkpoint runs under `db.transaction()` with a lease check; candidate updates, daily counts, snapshots, and final progress commit together under the existing shared lock.
- Candidate status, existing listings, pause switches, and the daily quota are re-read inside that transaction. Existing pending candidates may receive evidence after the new-candidate quota is full; rejected/approved IDs never silently re-enter the queue. Quota-deferred IDs remain in private run evidence, and star observations continue without adding candidates beyond the quota.
- Quotas use the actual local insertion date in the current configured timezone, including resumed jobs crossing midnight. The default remains 10 new candidates per local day; owner-configured limits are retained. First star observations have null absolute/proportional growth; zero-star baselines have no proportional growth. Growth signals remain separate.
- Jev receives bounded metadata as untrusted evidence and can propose category, suitability, NSFW status, and uncertainty. Decisions never confirm free-use eligibility or publish anything. Empty category lists omit the category question. Missing/disabled Jev still permits private evidence collection; strict configured-provider failures continue to stop the affected job for owner review.

## Integration requests and remaining limits

1. **Unknown software type:** `Metadata.type` defaults to `"Desktop app"`, and the shared schema/UI offer no unknown value. This lane cannot represent an absent upstream type without that default. The integrator should add an unknown representation or require explicit owner type confirmation before publication. No model, frontend, or schema files were changed here.
2. **Checkpoint compatibility:** Session 4 must retain the original saved mapping and the additive `collection`, `coverage`, `repositoryLimit`, `evaluated`, `seenRepoIds`, `unavailable`, `quotaDeferred`, and `evaluationLimitReached` fields on resume. Their values are private run evidence, not public catalog metadata. The baseline already provides the needed `assert_lease()` and transaction-aware `checkpoint(data)` methods; no new JobContext API is required.
3. **Legacy attempt history:** Old checkpoints recorded completed indexes only. Their initial new counter uses that index; unrecorded attempts before this change cannot be reconstructed. New attempt counts are durable, but a failed call may exhaust the remaining allowance without producing another candidate.
4. **Coverage:** At most nine root-topic queries rotate each run, alongside three recent/active searches. Each discovery search requests at most 20 URLs; seeds retain priority and may occupy the whole queue. These are bounded star-sorted samples, not an exhaustive repository index or a guarantee of finding every small growing project. Legacy source coverage cannot be reconstructed. General search pagination is capped at four pages; GitHub truncation/incompleteness remains explicit.
5. **Preserved boundaries:** Configured-provider failures remain strict so the existing runner can require owner response. The existing shared transaction/advisory lock is reused; no second AI reservation or persistence abstraction was introduced. Integration must preserve that locking and lease ownership behavior. Discovery quota accounting intentionally uses actual insertion day rather than a resumed runner's potentially stale/different `local_day`.
6. **Verification limits:** Per the handoff, no application tests, live GitHub/Jev calls, notifications, database initialization/migrations, scheduled worker execution, frontend build, merge, push, or deployment were performed. Compilation/imports and author review do not prove network/provider behavior, prompt-injection resistance, concurrency, crash recovery, DST, or PostgreSQL behavior. No independent reviewer was used because this lane forbids starting additional sessions. No unrelated minor findings were deferred.
